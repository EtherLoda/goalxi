## 0. 现状盘点

### 已完成（`208adc4`）

- `stadium.level` 1–5，容量上限 20,000 / 40,000 / 60,000 / 80,000 / 100,000
- 扩建超过本级上限会被拒，报错带「差在哪一级」
- `POST /teams/:id/stadium/upgrade`，owner-only，走同一条施工队列（`kind=UPGRADE`）
- 完工通知新增 `notification.stadiumUpgradeCompleted`（zh/en）
- 收入口径未变：等级不乘任何系数，仍是「容量 × 上座率 × 票价」

### 前端缺口

| 缺口 | 后果 |
|---|---|
| 页面不显示等级 | 玩家不知道自己卡在哪一级 |
| 没有升级入口 | 容量到 20,000 后无路可走，只能用 API |
| 扩建对话框不知道上限 | 能拖到 25,000 提交，然后被 400 打回 |
| 收入卡与容量格子重复显示容量 | 同样的数字出现两遍 |

## S1 等级接进前端（0.5 天）

1. 球场名右侧 `LevelBadge`：`3 / 5 级`
2. 容量格子加副行 `上限 60,000`
3. 主操作 `升级球场`，副行写 `£1,500,000 · 4 周`；满级、已有工程、钱不够三种情况各自给出禁用的原因
4. `ConstructionDialog`：滑块上限改成 `capacityCap`，并显示 `本级上限 60,000（升到 4 级解锁 80,000）`
5. i18n：`levelLabel` / `upgradeCta` / `upgradeLockedMax` / `upgradeLockedBusy` / `capNote`，zh + en

**验收**：1 级时在对话框里就拖不到 20,001，不会先提交再报错；升到 2 级后 40,000 可用。

## S5 可选扩展（后置，取决于 P1）

- 看台命名 / 冠名赞助（纯表现 + 少量收入，注意别又变成线性加钱）

## 风险

- **老数据**：现在已有球队容量可能高于 40,000。迁移按 `ceil(capacity / 20000)` 回填等级并夹在 1–5，超过 100,000 的会被压到 5 级但容量不动，需要一次人工核对。
- **bot 球队**：seed 容量 5,000，落 1 级，不受影响。
- **收入没变**：这次不碰票价和上座率，所以财务报表、周结算、attendance 预测都不需要回归——但 S2 重排要保证两个收入数字的口径和 P0 一致。
